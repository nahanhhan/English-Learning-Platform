## Context

**现有发音能力**：`frontend/src/speak.ts` 导出 `speak(text, accent)`，主通道为有道 dictvoice 在线音频，`play()` 失败时调用内部函数 `fallbackSpeak` 降级为浏览器本地语音合成；模块内有一个 `currentAudio` 变量，新播放会先 `pause()` 掉上一个。

**现有发音入口**：`Study.tsx` 里的 `AccentButtons`（「英」「美」两个按钮），只出现在四处——学习题面、拼写环节、测验题面、词表行（第 307 / 345 / 536 / 605 行）；卡片结算页（`stage === 'done'`，第 373–400 行）只有「下一张」，没有发音按钮。

**学习流的状态机**（`Study.tsx`）：`cards = [...queue.review, ...queue.new]`，当前卡为 `cards[queueIdx]`；`stage` 在 `choice → spell → done` 之间流转；`nextCard()` 前进下标，走完队列时重新拉取队列并把下标归零；`resetCardState()` 把 `stage` 置回 `choice`；评分为 `good` 时 `finishCard` 会在 1 秒后自动调用 `nextCard()`。今日队列与错题专项练习共用这套渲染，仅 `source` 不同。

**队列加载的两个既有特点**（本设计必须处理）：
1. `loadQueue()` 在 `await` 取数据之前就先调用了 `resetCardState()` 和 `setQueueIdx(0)`（第 96–97 行），因此加载期间会先渲染出一帧「旧队列的第 0 张卡、`stage` 为 `choice`」。
2. `loadQueue` 的依赖含 `source`，而挂载它的 effect 依赖 `[tab, loadQueue]`；进出错题专项练习时按钮同时改了 `source`（或 `tab`）又直接调了一次 `loadQueue`，于是**一次点击会发出两次队列请求**，两个响应各自 `setQueue` 一个全新的队列对象。

**偏好存储**：后端 `user_settings` 键值表，`GET /api/settings` 返回 `prefs`（值均为字符串），`PUT /api/settings/prefs` 写入；前端设置页用 `Switch` 绑定，如 `prefs.mock_mode === '1'`。`Study.tsx` 目前不读取 `prefs`。

**路由与构建**：`App.tsx` 对每个页面做 `lazy` 按需加载，从设置页回到背单词页会重新挂载组件；`main.tsx` 启用了 `React.StrictMode`，开发模式下 effect 会被双调用；`vite.config.ts` 的 dev server 把 `/api` 代理到 127.0.0.1:8930。

## Goals / Non-Goals

**Goals:**

- 卡片进入题面即发声，用户零操作
- 同一张卡的每一次「出场」只发声一次；不同出场之间不受队列对象换代影响
- 与既有手动发音行为一致：同一来源、同一时刻只有一个声音
- 提供设置开关，默认开启；开关状态未知时不乱发声
- 发音失败绝不打断答题流程

**Non-Goals:**

- 不做语速、音量、音色选择，也不做单词与短语分开的自动发音开关
- 不做「等发音播完再显示题面」之类的同步，题面出现不被音频阻塞
- 不改拼写环节、测验页题面、词表行的手动发音按钮分布，也不给结算页新增按钮
- 不改后端队列与 SRS 逻辑

## Decisions

### D1 触发点选在「题面出现」，用 effect 监听而不是在前进函数里调用

用 `useEffect` 监听 `[tab, stage, currentCard, queueIdx]`，当处于学习 Tab、`stage === 'choice'` 且有当前卡时触发。

备选：在 `nextCard()` / `finishCard()` 里直接调用 `speak()`。否决原因——卡片前进有多个分支（正常前进、队列走完后重取、进出专项练习），逐个加调用容易漏；且重取队列后 `currentCard` 要等下一次渲染才更新，函数内取不到正确的词。effect 以「渲染结果」为准，所有分支自动覆盖。

### D2 去重靠「队列代次 + 下标」，并先解决陈旧帧与重复请求

单靠「每次 `setQueue` 得到的对象引用」做标识是不行的，原因见 Context 的两条既有特点：加载期间会渲染出旧队列第 0 张的那一帧，而一次点击发出的两个请求会产生两个对象、两个标识。三处一起改：

1. **丢弃过期响应**：`loadQueue` 里加一个自增的请求序号，响应回来时若序号不是最新的就整段丢弃，不 `setQueue`。这样一次点击的两个请求只有最后一个会被采用。这是修既有缺陷——目前两个响应会依次 `setQueue`，中间的旧队列闪现本就不该存在。
2. **加载期间不发音**：用一个 ref 标记「队列正在加载」，effect 在此期间直接返回。这样第 1 条特点里那一帧旧卡不会被念出来（否则换词书、切回学习 Tab 时会先念旧书的第一个词，几百毫秒后被新词打断）。
3. **出场标识 = 队列代次 + 下标**：每采用一个新队列，代次加一；标识为 `代次 + 下标`。用 `useRef` 记下最后已自动发音的标识，相同就跳过。

为什么代次能同时满足两个相反的要求：同一代次内下标不变表示「还是同一张卡」，跳过——对应「同一张卡停留不重复播放」；队列被重新采用（答错重排、切词书、切 Tab 回来、进出专项练习）后代次一定变，于是同一张卡再次出现时会重播——对应「答错的卡片再次轮到」；而第 1 条丢弃过期响应保证了一次点击不再产生两次采用，所以不会连读两遍。

备选：以卡片 ID 去重。否决原因——切到词表 Tab 再切回来、或词书里只有一张卡时，同一张卡再出现就不会发声，与规格的「再次轮到」语义不符。

`useRef` 与代次配合也顺带覆盖了 `StrictMode`：开发模式下 effect 双调用会发两个请求，但请求序号让只有最后一个被采用，代次只加一次，因此只读一遍。这条不靠 ref 的跨重挂载特性，属结构性保证。

### D3 开关的读取方式：背单词页挂载时读一次 `/api/settings`，读到之前按关闭处理

`Study.tsx` 挂载时请求 `GET /api/settings`，取 `prefs.auto_speak`。由于页面是路由级 `lazy` 加载，从设置页返回时会重新挂载并重新读取，开关改动天然生效。

未读到之前（请求在途或失败）按「关闭」处理，不用「默认开启」兜底。理由：规格承诺的是「开关关闭时不发声」，若在设置未回来时按开启兜底，用户关掉开关后回到学习页的第一张卡仍会响，等于承诺落空。代价是设置接口失败时自动发音静默失效——本项目的设置与学习接口同源，接口失败时整个页面本就不可用，这个代价可以接受。

备选一：提到 `App` 层做全局状态或 Context。否决原因——只为这一处用途引入全局状态不划算。
备选二：存 `localStorage`。否决原因——与既有偏好机制分裂成两套，且与「偏好保存在本地数据库」的既有约定冲突。

### D4 后端偏好键沿用键值表，缺省即开启

`GET /api/settings` 的 `prefs` 增加 `auto_speak`，读取用现有的 `get_setting(db, "auto_speak", "1")`，`PrefsBody` 增加 `auto_speak: bool | None`，`PUT /api/settings/prefs` 增加对应分支，写 '1'/'0'，与 `mock_mode` 完全同构。旧数据库没有该记录时按默认开启处理，无需迁移。

注意：前端拿到的 `prefs` 值是字符串，判断须写 `prefs.auto_speak === '0'` 这类比较，不能当布尔用（D3 的 fail-closed 就是「没拿到 = 不发声」）。

### D5 打断发音时不再降级补念（修既有缺陷）

`speak.ts` 现在的写法是：先 `pause()` 旧音频，再播新的；但旧音频的 `play()` 若尚未开始播（还在缓冲），`pause()` 会让它以 `AbortError` 拒绝，于是它的 `.catch()` 触发，**无条件**调用 `fallbackSpeak(旧词)`——结果是上一个词用浏览器本地合成音念出来，和正在播的新词叠在一起。`onerror` 分支同理（旧音频加载失败时也会补念）。

修法：两处降级前都先判断「这个音频是否还是当前音频」，不是就直接返回，不再补念。这与既有主规格「同一时刻只播放一个音频」的承诺一致，不改变规格。

自动发音会显著抬高触发概率：换卡自动出声后，用户常在几百毫秒内就点了「美」或按了下一次换卡，正好落在旧音频还在缓冲的窗口里。

### D6 离开学习流时停止播放

`speak.ts` 增加一个停止入口（停掉当前音频并清空引用），`Study.tsx` 在切离学习 Tab、以及组件卸载时调用。规格新增了对应要求。

理由：自动发音让「有声音在播」成为常态，用户点「测验」Tab 时短语可能还要念两三秒，声音跟到测验页会与「测验页不自动发音」的意图直接冲突。

### D7 不实现「手势解锁后补播」

页面刚打开、用户尚未有任何点击或按键时，浏览器自动播放策略可能拒绝出声，此时第一张卡听不到声音。不额外做补播。

理由：需求是「跳到下一个单词时发声」，页面初始的第一张卡不是跳转动作；补播会让用户在几秒后突然听到声音，反而突兀。之后的卡片通常紧跟在点击选项或按键之后，具备用户交互，不受影响。详见 Risks。

## Risks / Trade-offs

- **浏览器自动播放策略拒绝出声（页面刚打开的第一张卡）** → 静默跳过（D7）。若实测发现每次会话首卡都无声且用户介意，再单独提变更加「手势解锁补播」。
- **设置接口失败导致自动发音静默失效** → D3 的有意取舍：宁可不出声，也不能在用户关掉开关后还出声。设置页的开关本身仍正常显示。
- **每张卡都发声造成干扰** → 提供设置开关，默认开启，随时可关。
- **网络延迟导致声音晚到，听起来慢半拍** → 不阻塞界面；在线音频通常数百毫秒内返回，可接受。
- **丢弃过期响应对既有行为的影响** → 只影响「同一时刻有多个队列请求在飞」的情形，采用最新一个本来就是期望结果；改动限于 `loadQueue` 内部。
- **短语比单词长，自动发音的听感** → 见 Open Questions。

## Migration Plan

- 无数据迁移：旧数据库缺 `auto_speak` 记录时按默认开启处理。
- 回滚：还原 `Study.tsx`、`Settings.tsx`、`speak.ts`、`settings.py` 四个文件即可。残留的 `auto_speak` 记录不被旧代码读取，无害。

## Open Questions

- 短语比单词长，自动发音的听感是否可接受，需要实现后实听判断。若不可接受，再单独提变更把开关细化到「单词 / 短语」分开控制——这不影响本次的规格与实现。
